\begin{abstract}
本書は AIPL（ABCL$^{c}$+）の\textbf{現状の}ユーザーズガイドである。
第 \ref{part:start} 部で言語の全体像と最短の動かし方、
第 \ref{part:lang} 部で文法と型システムの仕様、
第 \ref{part:disciplines} 部でその上に載る七つの規律を、
第 \ref{part:sample} 部でサンプルプログラムをソースと実行結果つきで、
第 \ref{part:tool} 部でビルド・実行・検査の道具立て（\textbf{ベアメタルの Raspberry Pi 3 で動かす手順}を含む、\S\ref{sec:xinu}）を、
第 \ref{part:appendix} 部に文法の要約・現状の限界・旧版からの移行を置く。

AIPL は\textbf{アクター}を単位とする並行言語で、値は \texttt{return} ではなく
\texttt{reply} で返す。その上に三つの静的な仕組みが載っている ---
\textbf{型}（\texttt{reply} から戻り値型を推論し、注釈も書ける）、
\textbf{効果}（\texttt{!\{ai, net\}} のようにメソッドが世界に及ぼす作用を宣言する）、
\textbf{期限}（\texttt{now ... timeout ... else ...} で待ちに上限を置く）。
たとえば「実時間で動くアクターが、機外のモデルを同期で呼ぶ」ことは、
効果検査だけで禁止できる。

さらにその上に\textbf{七つの規律}が載っている（第 \ref{part:disciplines} 部）---
失敗の型 \texttt{result}$\langle\tau\rangle$、返信先の一級性、資源の順序、
義務レベル、セッション型である。
どれも\textbf{注釈を書かなくても効く}ように作ってある。
その結果、\textbf{待ちの宛先がクラスとして分かるか、
宛先ノードのレベルが宣言されている範囲では、デッドロック自由が型で保証される}。
これは紙の上だけの主張ではなく、Coq/Rocq で機械検証してある。

本書が述べるのは、三つの処理系（OCaml 版・Python 版・JavaScript 版）
すべてが備える\textbf{核}である。Python 版はこれに記録型・精緻化型・
チャネル・所有などの\textbf{拡張}を持っており、言語は二層になっている
（\S\ref{sec:migrate}）。

前版（2026年07月30日版）からの差分だけを知りたい場合は
\S\ref{sec:migrate} を見ればよい。\texttt{become} は\textbf{言語から外した}。
\end{abstract}

\part{はじめに}
\label{part:start}

\section{AIPL とは}

AIPL は ABCL/1 の系譜にあるアクター言語である。プログラムは
\textbf{クラス宣言}と\textbf{グローバル文}の並びで、クラスから生成された
アクターがメッセージを送り合って動く。

\begin{lstlisting}
class Counter {
  var n = 0;                       // フィールド（アクターの状態）
  method bump() : int !{mut} {     // 戻り値型 int、効果は mut
    n = n + 1;
    reply(n);                      // 呼び出し側へ値を返す
  }
}

var c = new Counter();             // アクターを1台つくる
print(now c.bump() timeout 100 else 0);
\end{lstlisting}

他の言語との違いのうち、最初に押さえるべきものは四つある。

\begin{enumerate}
\item \textbf{アクターは 1 台 1 スレッド}で、受け取ったメッセージを
  逐次に処理する。フィールドへの同時アクセスは起こらない。
\item \textbf{値は \texttt{reply} で返す。} \texttt{return} は無い。
  \texttt{reply} は呼び出し側の future を解決する操作で、
  メソッドの実行はその後も続けられる。
\item \textbf{送信には三種類ある。} \texttt{send}（待たない・文）、
  \texttt{now}（返信まで待つ・式）、\texttt{future}（待たずに引換券を得る・式）。
\item \textbf{待つと固まる。} \texttt{now} で待っている間、そのアクターは
  他のメッセージを一切処理できない。だから待ちには期限を書く。
\end{enumerate}

\section{三つの静的な仕組み}

\subsection{型 --- 何を返すか}

メソッドの戻り値型は本体の \texttt{reply} から推論される。
省略可能な注釈 \texttt{method m(x) : T} も書ける。
注釈を書くと、全実行パスで \texttt{reply} することが検査され、
かつ宣言した型が\emph{期待型}として式の推論に流れる。

\subsection{効果 --- 世界に何をするか}

メソッドが持つ作用を \eff{...} で宣言する。効果は 8 種類ある
（\S\ref{sec:effects}）。省略すると本体から推論され、
書けば「本体の効果 $\subseteq$ 宣言した効果」が検査される。

\begin{lstlisting}
method plan(goal) : string !{ai, net} { reply(ai_call("plan: " ++ goal)); }
method peek()     : int    !{}        { reply(n); }
\end{lstlisting}

\texttt{ai} と \texttt{net} を分けてあるのが要点で、
「AI を使うが機外へは出ない」オンデバイス推論を \eff{ai} だけで表せる。

\subsection{期限 --- いつまで待つか}

\begin{lstlisting}
var r = now planner.plan(g) timeout 2000 else "(timed out)";
\end{lstlisting}

期限内に返信が来なければ \texttt{else} 節の値になる。
\texttt{else} を書かなければ \texttt{result}$\langle\tau\rangle$ が返り、
確かめずには使えない（\S\ref{sec:result}）。

\subsection{そのうえに七つの規律がある}

型・効果・期限は土台である。その上に、失敗の型・返信先の一級性・
資源の順序・義務レベル・セッション型が載っている
（\S\ref{part:disciplines}）。
どれも\textbf{注釈を書かなくても効く}ように作ってある。
その結果、\textbf{待ちの宛先がクラスとして分かるか、
宛先ノードのレベルが宣言されている範囲では、デッドロック自由が型で保証される}
（\S\ref{sec:levels}）。

\part{言語ガイド}
\label{part:lang}

\section{プログラムの構成}

プログラムは\textbf{宣言の並び}である。宣言は次のいずれかで、
順序は自由だが、参照する名前は実行時に解決される。

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
宣言 & 内容 \\
\midrule
\texttt{class C \{ ... \}}            & クラス定義 \\
\texttt{var x = e;}                   & グローバル変数 \\
\texttt{var x = new C(args);}         & アクターの生成 \\
\texttt{send t.m(args);}              & グローバルな非同期送信 \\
\texttt{send! t.m(args);}             & 同上（検査を緩めた送信） \\
\texttt{f(args);}                     & 組込み関数の呼び出し \\
\bottomrule
\end{tabular}
\end{center}

\begin{quote}\small
グローバルの位置に \texttt{if} や \texttt{while} は書けない。
制御構造が必要ならメソッドの中に置いて \texttt{send} で起動する。
\end{quote}

クラスは\textbf{フィールドの並び}に\textbf{メソッドの並び}が続く形である。

\begin{lstlisting}
class Counter {
  var n = 0;                    // フィールドは先。var か float で宣言する
  float ratio = 1.5;
  method init(start) {          // init は new のときに自動で呼ばれる
    n = start;
  }
  method bump() : int !{mut} {
    n = n + 1;
    reply(n);
  }
}
\end{lstlisting}

\begin{itemize}
\item フィールドはメソッドより\textbf{前}に書く。
\item クラスには\textbf{メソッドが最低 1 つ}必要である（文法上、
  フィールドだけのクラスは書けない）。
\item \texttt{init} という名前のメソッドは \texttt{new C(args)} のときに
  自動で呼ばれる。引数の個数が合わないと生成が飛ばされ、
  \texttt{[Actor] x: no init; skipped} と表示される。
\item フィールドの初期化式で型が決まる。\texttt{var n = 0;} は \ty{int} に
  なるので、あとから \ty{float} や文字列を代入すると型エラーになる。
\end{itemize}

\section{型}

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
型 & 説明 \\
\midrule
\ty{int}, \ty{float}, \ty{string}, \ty{bool}, \ty{unit} & 基底型 \\
\ty{T[]}          & 配列（\texttt{array\_*} 組込みで扱う） \\
\ty{future\ T}    & \texttt{future} 送信の結果。\texttt{await} で \ty{T} を取り出す \\
\ty{actor(C)}     & クラス \texttt{C} のアクター。\texttt{new C(...)} の型 \\
\ty{any}          & 静的に内容を保証しない境界（\texttt{sender}、リモート送信先） \\
\bottomrule
\end{tabular}
\end{center}

戻り値型注釈に書けるのは
\texttt{int} / \texttt{float} / \texttt{string} / \texttt{bool} /
\texttt{unit} / \texttt{any} と、大文字で始まるクラス名（アクター型）である。
小文字で始まる未知の名前は
\texttt{unknown type name in return annotation} として構文エラーになる。

\begin{quote}\small
\textbf{メソッドの引数は単相である。} シグネチャの引数型変数は
全呼び出し地点で共有されるので、同じメソッドを \ty{int} と \ty{string} で
呼ぶと衝突する。多相なメソッドは書けない。
\end{quote}

\begin{quote}\small
\ty{int} と \ty{float} の間に\textbf{暗黙変換は無い}。
\texttt{var h = new Hello(5);} が \texttt{float} のフィールドに繋がると
型エラーになるので、\texttt{new Hello(5.)} と書く。
\end{quote}

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
式 & 意味 \\
\midrule

\texttt{x} & 変数・フィールド・仮引数 \\
\texttt{-\,e} & 単項マイナス。\texttt{neg(e)} へ落ちる。\ty{int}/\ty{float} \\
\texttt{a ++ b} & 文字列連結（両辺を文字列化）\\
\texttt{a + b}, \texttt{a - b}, \texttt{a * b} & 数値演算。\ty{int} 同士は \ty{int}、
  \ty{float} 同士は \ty{float} \\
\texttt{a / b} & 除算。\ty{int} 同士でも \ty{float}（整数除算はしない） \\

\end{tabular}
\end{center}

送信先 \texttt{t} は\textbf{アクター参照が入った変数名}か
\texttt{remote("host:port", "actorName")} である。クラス名ではない。

\subsection{優先順位}

弱い順に

\begin{center}
等値 \texttt{==} \texttt{!=} \ $<$\ 比較 \texttt{>} \texttt{<} \texttt{>=} \texttt{<=}
\ $<$\ 連結 \texttt{++} \ $<$\ 加減 \texttt{+} \texttt{-}
\ $<$\ 乗除 \texttt{*} \texttt{/} \ $<$\ 単項マイナス
\end{center}

である。したがって \texttt{1 + 2 == 3} は \texttt{(1 + 2) == 3}、
\texttt{"x=" ++ a + b} は \texttt{"x=" ++ (a + b)} と読まれる。
二項演算子は\textbf{すべて左結合}である（等値も含む）--- \texttt{1 == 2 == false} は \texttt{((1 == 2) == false)} と読まれて \texttt{true} になる。単項マイナスは前置なので重ねられる（\texttt{- - 3} は \texttt{3}）。

\subsection{\texttt{+} と \texttt{++} を混同しない}

\texttt{+} は\textbf{数値専用}である。文字列を混ぜると
\texttt{no overload of + matches (string, int)} になる。

\begin{lstlisting}
print("count = " ++ n);      // 正しい
print("count = " + n);       // 型エラー
\end{lstlisting}

\texttt{++} は両辺を文字列化してから連結するので、どちらが文字列でなくてもよい。

\subsection{曖昧なオーバーロード}

両辺が未束縛の \texttt{a + b} は \ty{int} とも \ty{float} とも解釈でき、
principal type を持たない。これはエラーである。注釈を書けば
期待型が式へ流れて一意に決まる。

\begin{lstlisting}
method add(a, b)       { reply(a + b); }   // エラー: ambiguous overload
method add(a, b) : int { reply(a + b); }   // 注釈で確定する
\end{lstlisting}

\texttt{AIOS\_LAX\_OVERLOAD=1} で従来の「警告して既定候補を選ぶ」動作に戻せる。
等値 \texttt{==} \texttt{!=} は候補が 4 つあるが戻り値がすべて \ty{bool} なので
曖昧にはならない（曖昧判定は\emph{戻り値型が割れたとき}だけ行う）。

\section{文}

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
文 & 意味 \\
\midrule
\texttt{var x = e;} & 変数宣言 \\
\texttt{var x = new C(args);} & アクター生成つき宣言 \\
\texttt{x = e;} & 代入 \\
\texttt{f(args);} \quad \texttt{call f(args);} & 組込み関数の呼び出し \\
\texttt{send t.m(args);} & 非同期送信。返信を待たない \\
\texttt{send self.m(args);} & 自分自身への非同期送信 \\
\texttt{send sender.m(args);} & 送信元への非同期送信 \\
\texttt{send! t.m(args);} & 検査を緩めた送信 \\
\texttt{if (e) s} \quad \texttt{if (e) s else s} & 条件分岐（括弧が要る） \\
\texttt{while e do s} & 繰り返し（括弧は要らない） \\
\texttt{\{ s ... \}} & ブロック \\
\texttt{select \{ ... \}} & メッセージの選択受信 \\
\bottomrule
\end{tabular}
\end{center}

\begin{quote}\small
\texttt{now self.m()} と \texttt{now sender.m()} は\textbf{文法上書けない}。
自分への \texttt{now} は自己デッドロックになる（自分は今そのメソッドを
処理中なので、返信を作る主体がいない）ので、書けないことがそのまま
安全側に働いている。幾何計算などを別に切り出したいときは、
別アクターに置いて \texttt{now kin.solve(...)} と呼ぶ。
\end{quote}

\begin{quote}\small
\texttt{var x : T = e;} という型注釈つきの変数宣言は\textbf{まだ無い}。
仕様案にはあるが未実装である。
\end{quote}

\section{アクターと通信}

\subsection{三つの送信}

\begin{center}
\begin{tabular}{@{}llll@{}}
\toprule
 & 待つか & 式か文か & 呼ばれる側の効果を負うか \\
\midrule
\texttt{send a.m(x);}      & 待たない     & 文 & 負わない \\
\texttt{now a.m(x)}        & 返信まで待つ & 式（結果は宣言／推論された型） & \textbf{負う} \\
\texttt{future a.m(x)}     & 待たない     & 式（\ty{future\ T}） & 負わない \\
\bottomrule
\end{tabular}
\end{center}

「待つ側だけが呼ばれる側の効果を負う」というのが効果伝播の規律である
（\S\ref{sec:effects}）。

\subsection{\texttt{reply}}

メソッドは値を「返す」のではなく \texttt{reply(v)} で呼び出し側の future を
解決する。型システムはメソッドごとに戻り値型を持ち、本体のすべての
\texttt{reply} と、すべての \texttt{now} / \texttt{future} 送信地点が
この型を共有する。

\begin{itemize}
\item \texttt{reply} は\textbf{高々一度}。2 度目は待ち手がすでに 1 度目の値を
  受け取ったあとに来るので黙って捨てられる。これは型エラーにしてある。
\item 戻り値型を \ty{unit} 以外で\emph{宣言}した場合は、
  \textbf{全実行パスでちょうど一度}になることが検査される。
  \texttt{while} の本体は 0 回実行されうるので、保守的に「reply しない
  パスがある」と判定される。
\item \texttt{reply} がまったく無いメソッドは戻り値 \ty{unit} と扱われる。
  \texttt{send} で呼ぶ「通知」型のメソッドがこれにあたる。
\end{itemize}

\begin{lstlisting}
method m(k) : int { reply(k); reply(k + 1); }                     // 型エラー
method m(k) : int { if (k > 0) { reply(1); } else { reply(2); } } // OK
\end{lstlisting}

\subsection{\texttt{select}}

\begin{lstlisting}
select {
  case job(k) -> { reply("done:" ++ k); }
  timeout 500 -> { print("timed out"); }
}
\end{lstlisting}

\texttt{case m(x1, ..., xn)} は同名メソッドの署名に照合される。
引数の個数と型が合わないと型エラーになる。
\texttt{timeout} の単位はミリ秒で、省略できる。

\textbf{case 本体の \texttt{reply} は、囲むメソッドではなく
「選択されたメッセージ」への返信である。}
処理系が case の実行前に返信先を選択されたメッセージへ切り替えるためで、
上の例の \texttt{reply} は \texttt{job} への返信になる。したがって
\texttt{select} を含むメソッド自身は \ty{unit} でよい。
一方 \texttt{timeout} 本体は囲むメソッドの返信先のまま実行される。

\begin{quote}\small
\texttt{select} は\emph{まだ処理されていない}メッセージを mailbox から探す。
通常のメソッド dispatch が先に同名メッセージを取ってしまうと
case には残らないので、\texttt{select} で待つ名前は直接呼ばせない設計に
するのが安全である（\S\ref{sec:g4} の実行結果を参照）。
\end{quote}

\section{期限付きの待ち}
\label{sec:deadline}

\subsection{なぜ必要か}

\texttt{now} や \texttt{await} を期限なしで書くと、返信が来なければ
永久に待つ。アクターは 1 台 1 スレッドで、待ちは条件変数でブロックするので、
待っている間そのアクターは他のメッセージを一切処理できない。石になる。

\begin{lstlisting}
now t.m(a) timeout <ミリ秒> else <式>
await f    timeout <ミリ秒> else <式>
\end{lstlisting}

期限内に返信が来ればその値、来なければ \texttt{else} 節を評価した値になる。

\subsection{規則}

\begin{itemize}
\item \texttt{else} 節は\textbf{本体と同じ型}でなければならない。
  期限切れでも式全体の型は変わらないためである。
  違うと \texttt{now: the else branch has type string but the call returns int}。
\item 期限は\textbf{正}でなければならない（\texttt{timeout must be positive}）。
\item 期限なしの \texttt{now} / \texttt{await} は既定では\textbf{警告}で、
  \texttt{AIOS\_STRICT\_DEADLINE=1} で\textbf{エラー}になる。
\item \texttt{reply} 回数の上界は、本体と \texttt{else} の
  \emph{どちらか一方}が走るとみなして \texttt{max} を取る（和ではない）。
\item 拒否された future（\texttt{reject}）は期限切れとは区別され、例外になる。
\end{itemize}

実装では OCaml の \texttt{Condition} に時限待ちが無いので、1\,ms 刻みの
ポーリングで期限を測っている。

\subsection{型健全性との関係}
\label{sec:soundness}

期限を書くと、待ちは有限時間で終わる。ただしこれは
\emph{デッドロックが有限時間の失敗に変換される}ということであって、
失敗が消えるわけではない。互いに \texttt{now} で待ち合う二者は両方が期限切れになる。
詰まらないが正しくもない。

\textbf{詰まらないこと自体}を型で言うには、期限ではなく
\textbf{義務レベル}が要る（\S\ref{sec:levels}）。
そちらは \textbf{Coq/Rocq で機械検証してある} ---
\texttt{await} を含んだままの中核について、
型健全性・型安全性・デッドロック自由の三つを、公理なしで証明した
（\texttt{coq/AIPLSoundness2.v}）。
第 1 版は \texttt{await} を言語から取り除いた断片でしか
デッドロック自由を言えていなかったので、そこが第 2 版の要点である。

進行定理は次のように変わった。

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
& 進行定理の主張 \\
\midrule
第 1 版 & 終状態 $\lor$ 一歩進める $\lor$ \textbf{全タスクが待ち} \\
第 2 版 & 終状態 $\lor$ 一歩進める \\
\bottomrule
\end{tabular}
\end{center}

停止性は依然として言えない。\texttt{while 1 > 0 do \{\}} は止まらないが、
それは待ちではないので、進行定理とは矛盾しない。

型システムの上で機械的に効くようになったということである。

\begin{quote}\small
\textbf{既知の穴。} \texttt{now} を \texttt{future} と \texttt{await} に

伝播の辺を張らず、\texttt{await} では伝播させていないためである。
再現は \texttt{docs/samples/}\allowbreak\texttt{soundness2\_effect\_gap.aipl}
にある。
修正方針（\ty{future} の型に効果を載せる）は第 2 版の報告書に書いてある。
\end{quote}

\part{七つの規律}
\label{part:disciplines}

型・効果・期限の上に、七つの規律が載っている。
どれも\textbf{注釈を書かなくても効く}ように作ってある ---
必要な情報は、たいていプログラムの中に既に書かれているからである。

\begin{center}
\small
\begin{tabular}{@{}lp{5.6cm}p{4.0cm}@{}}
\toprule
規律 & 書き方 & 止めるもの \\
\midrule
効果 & \texttt{!\{ai, net\}} & 実時間側が機外のモデルを待つこと \\
期限 & \texttt{timeout $n$ else $e$} & 返らない待ち \\
失敗の型 & \texttt{timeout $n$}（\texttt{else} 無し） & 期限切れの値を正常値として流すこと \\
返信先の一級性 & \texttt{replyto} / \texttt{answer} / 引数型 \texttt{reply} & 返信の取りこぼしと二重返信 \\

義務レベル & \texttt{@$n$}（書かなければ推論） & 待ちの循環 \\

\bottomrule
\end{tabular}
\end{center}

\section{失敗を型に出す --- \texttt{result}$\langle\tau\rangle$}
\label{sec:result}

期限つきの待ちで \texttt{else} を書くと、時間切れの値と正常な値が
\textbf{同じ型}になる。$-1$ が返ったのか、正しく $-1$ が計算されたのかを
プログラムが問えない。

\texttt{else} を書かなければ \texttt{result}$\langle\tau\rangle$ が返る。

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
書き方 & 型 \\
\midrule
\texttt{now a.m(x) timeout 200 else -1} & \ty{int} \\
\texttt{now a.m(x) timeout 200} & \texttt{result}$\langle$\ty{int}$\rangle$ \\
\bottomrule
\end{tabular}
\end{center}

取り出しには \texttt{is\_ok} / \texttt{timed\_out} / \texttt{value} を使う。

\begin{lstlisting}
var a = now s.fast(42) timeout 200;      // result<int>
if (is_ok(a)) { print("fast ok " ++ value(a, -1)); }
else          { print("fast timed out"); }
\end{lstlisting}

\texttt{result}$\langle\tau\rangle$ は数値としては使えない。
確かめずに計算へ流すと止まる。

\begin{term}
no overload of + matches (result int, int)
\end{term}

\section{返信先を一級の値にする}
\label{sec:reply1st}

\texttt{replyto} は、いま処理しているメッセージの返信先を値として返す。
型は \texttt{reply}$\langle\rho\rangle$（$\rho$ はそのメソッドの戻り値型）で、
\texttt{answer(r, v)} で返信する。\texttt{reply(v)} はその糖衣にあたる。

引数の型注釈 \texttt{reply} を書くと、他のアクターへ渡せる。
窓口役が受けて、専門役が\textbf{直接}答える形が書ける。

\begin{lstlisting}
class Backend {
  method handle(r: reply, x) : unit !{} {
    answer(r, x * 2);            // Frontend の依頼者へ直接返す
  }
}
class Frontend {
  var b = new Backend();
  method ask(x) : int !{} {
    send b.handle(replyto, x);   // 返信先を渡して義務を移す。自分は reply しない
  }
}
\end{lstlisting}

返信先は\textbf{線形}に扱われる。ちょうど一度使うのが義務である。

\begin{center}
\small
\begin{tabular}{@{}lp{7.6cm}@{}}
\toprule
規律 & 内容 \\
\midrule
生成 & \texttt{var r = replyto;} で義務が生まれる \\
消費 & \texttt{answer(r, v)} するか、送信の引数として渡すと義務が消える \\
一度だけ & 同じ \texttt{r} を二度使ってはならない \\
残さない & メソッドを抜けるとき義務が残っていてはならない \\
枝 & \texttt{if} の二つの枝は同じ状態で合流する \\
\bottomrule
\end{tabular}
\end{center}

\begin{quote}\small
検査はメソッド内で閉じている。返信先を\textbf{フィールドに保持する}ことはできない
（フィールドは初期化子から型が決まるため）。
「送り主を溜めて後で返す」有界バッファのような書き方は、
いまのところ核では直接には書けない。
\end{quote}

\section{資源の順序}
\label{sec:resorder}

効果は\textbf{集合}なので、順序を表せない。「取ったら放す」が言えない。
そこで \texttt{acquire} / \texttt{release} の対を本体の中で追う。

\begin{lstlisting}
class Bus {
  var n = 0;
  method read(addr) : int !{mut} {
    acquire("i2c");
    n = n + 1;
    var v = addr * 2;
    release("i2c");           // これを消すと型エラーになる
    reply(v);
  }
}
\end{lstlisting}

規律は三つ。メソッドを抜けるとき持ち物が残っていてはならない。
持っていない資源を放してはならない。二重に取ってはならない。
\texttt{if} の二つの枝は同じ持ち物で合流し、
\texttt{while} の本体は持ち物を変えない。

\subsection{全体順序 --- 逆順の取得を止める}

対の検査だけでは足りない。二つのアクターが同じ二つの資源を
\textbf{逆の順序}で取ると、どちらも対は正しいのに、実行すると互いを待つ。

新しい注釈は要らない。\textbf{$r$ を持っているあいだに $s$ を取った}という
入れ子が、そのまま $r < s$ という主張である。
プログラム全体から集め、閉路が無いことを見る。

\begin{term}
resource order: cache -> db -> cache is circular;
  cache before db (in Reader.run); db before cache (in Writer.run).
  Acquiring in opposite orders deadlocks
\end{term}

閉路の各辺が\textbf{どこで生まれたか}を持っているので、
逆順に取っている二か所がそのまま出る。

推論に任せず \texttt{resource\_order("bus -> dev")} と書くこともできる。
宣言は同じ表に辺として入るだけなので、宣言と実際の取得が食い違えば
それも閉路として出る。
推論した順序は \texttt{AIOS\_SHOW\_LEVELS=1} で見える。

\begin{term}
[resource] bus                  @0
[resource] dev                  @1
\end{term}

\begin{quote}\small
追えるのは資源の名前が\textbf{文字列リテラル}の \texttt{acquire} だけである。
変数に入った名前は静的には分からないので、宣言した順序は実行時にも効かせている
（\texttt{AIOS\_STRICT\_RESOURCE=1} で追えなかった場所を知らせる）。
\end{quote}

\section{義務レベル --- 待ちの循環を止める}
\label{sec:levels}

待ちが返らなくなる形は四つある。
循環待ち、返信されない待ち、\texttt{select} が来ないメッセージを待つ場合、
そして資源を逆順に取る場合である。
一つ目に効くのが\textbf{義務レベル}である。

各メソッドに番号を付け、\textbf{待ちは必ず番号の大きい方へ向かう}ことを要求する。

\begin{lstlisting}
class Leaf { method f(x)  : int @2 !{} { reply(x + 1); } }
class Mid  { var l = new Leaf();
             method g(x)  : int @1 !{} { reply(now l.f(x) timeout 200 else 0); } }
\end{lstlisting}

\textbf{書かなくてよい。}書かなければ、待ちの辺を見て押し上げる不動点で推論される。
明示注釈は固定点として扱い、動かせなければそこが矛盾である。

\begin{term}
obligation level: B9#g (@2) waits on A9#f (@2);
                  a wait must go to a strictly higher level
obligation levels do not converge; the wait graph has a cycle
\end{term}

推論したレベルは \texttt{AIOS\_SHOW\_LEVELS=1} で見える。

\subsection{ノードをまたぐ待ち}

メッシュでは宛先の実体が別ノードにあり、静的には見えない。
そこでノードごとにレベルの\textbf{下限}を宣言し、
そのノードへの待ちは必ず上へ向かうことを要求する。

\begin{lstlisting}
node_level("rt0", 10);            // 実時間ノードは葉（高いレベル）
\end{lstlisting}

\begin{term}
obligation level: Ctl2#go (@7) waits on node rt0 (floor @1);
                  a wait across nodes must go up
\end{term}

効果を \texttt{node\_allow} で国境で照合するのと、まったく同じ形である。

\subsection{どこまで保証されるか}

\textbf{待ちの宛先がクラスとして分かるか、宛先ノードのレベルが宣言されている
範囲では、デッドロック自由が型で保証される。}
この主張は紙の上だけではない ---
Coq/Rocq で、\texttt{await} を含んだままの中核について機械検証してある
（\texttt{coq/AIPLSoundness2.v}、公理なし）。

条件も書いておく。宛先が動的だと見えない。
レベルはメソッド単位なので、同じクラスの別インスタンス同士は一律に扱われる。
停止性と飢餓は別問題である。

\section{セッション型 --- やり取りの順序}
\label{sec:session}

「開いてから読み、最後に閉じる」という約束は、期限でも送り手の存在でも表せない。
AIPL には\textbf{実行時}のセッションプロトコルが既にあるので、
\textbf{同じ宣言}を型検査の側でも読む。新しい宣言は要らない。

\begin{lstlisting}
protocol_define("Pipeline", "f.get -> r.scale -> st.put");
var sid = protocol_start("Pipeline");

var a = now f.get(4)    timeout 200 else 0;
var b = now r.scale(a)  timeout 200 else 0;
var c = now st.put(b)   timeout 200 else 0;
protocol_end(sid);
\end{lstlisting}

順序を取り違えると、走らせる前に出る。

\begin{term}
protocol Pipeline: expected r.scale but the program sends st.put here
protocol Pipeline is incomplete at protocol_end; next expected st.put
\end{term}

（実際の出力の例）

\begin{term}
protocol P29: expected b.step2 but the program sends c.step3 here
\end{term}

\subsection{アクターをまたぐ場合}

実際のプログラムでは、手順は一つの並びに収まらない。
窓口役をひとつ呼び、残りの手順はその本体の中で進む。

同期の送信（\texttt{now} / \texttt{aios\_now}）は、呼び先が呼び出し側の続きより
\textbf{先に走り切る}。だから呼び先の送信列を、呼び出しの位置に
そのまま差し込んでよい（振る舞い展開）。
これで、またいだセッションも一本の並びとして照合できる。

非同期（\texttt{send} / \texttt{future}）は差し込まない ---
いつ走るか決まらないからである。
呼び先が手順を含んでいたら、完了の判定は実行時に任せる
（\texttt{AIOS\_STRICT\_PROTOCOL=1} で知らせる）。

\begin{quote}\small
手順は\textbf{名前}で役を指す。アクターを\textbf{引数で渡す}こと。
フィールドに持たせると、実行時の呼び名（\texttt{c\#f}）と
静的な呼び名（\texttt{f}）が食い違い、手順が役を指せない。
\end{quote}

\section{\texttt{select} の規律}
\label{sec:selectrule}

\texttt{select} には二つのことを課す。

\begin{enumerate}
\item \textbf{期限を書く}。\texttt{timeout} 節の無い \texttt{select} は、
  来ないメッセージを待ち続ける。
\item \textbf{送り手が居ることを確かめる}。
  \texttt{case m(...)} の \texttt{m} を、このプログラムの中で誰も送っていなければ、
  綴り間違いか書き忘れである。
\end{enumerate}

\begin{term}
select waits for W2.ghost but nothing in this program sends it
select without a timeout waits forever; write `timeout <ms> -> { ... }`
\end{term}

いずれも既定は警告である。送信が動的な場合や、外部に公開している
プログラムでは判断できないので、検査そのものを行わない ---
\textbf{言語が世界の全部を見ているわけではない}。

\section{メッシュ配備}
\label{sec:mesh}

アクターのソースを他ノードへ送り、\textbf{相手先で}構文解析・型検査してから
実体化する。効果注釈がコードと一緒に運ばれ、受け入れ側の方針と照合される。

\begin{lstlisting}
node_allow("rt0", "mut, log, time");     // 実時間ノードが受け入れる効果
deploy("rt0", "Servo", "servo1");        // Servo のソースを rt0 へ配って実体化
var d = now remote("rt0", "servo1").step(3) timeout 200 else -1;
\end{lstlisting}

\begin{term}
[deploy] Servo -> rt0/servo1 (compiled at destination)
\end{term}

\texttt{ai} や \texttt{net} を持つコードを実時間ノードへ配ると、国境で止まる。
効果が、単一ノード内の規律から\textbf{ノード間の入国審査}になる。

\emph{どの型を約束しているか}は宣言できる。

\section{g3: 複数アクターと、アクターを跨いだ \texttt{now}}

\lstinputlisting{samples/guide/g3_actors.aipl}

\begin{term}
ok, left=7
sold out
\end{term}

\texttt{Stock.take} が \ty{int} を返し、それが \texttt{Front.place} の中の
\texttt{now} の型になり、さらに \texttt{place} 自身の \ty{string} へ繋がる。
型はアクター境界を越えて伝播する。

\texttt{if} の両方の枝で \texttt{reply} していることが検査される。
片方を消すと \texttt{some execution path does not reply} になる。

なお \texttt{n = n - k} で \texttt{n} が \ty{int} なので \texttt{k} も
\ty{int} に決まり、呼び出し側の \texttt{place(3)} と整合する。
ここで \texttt{place("x")} と書けば\emph{引数の}型エラーになる。

\texttt{Front\#place} は \texttt{now} を通じて \texttt{Stock\#take} の
\eff{mut} を引き継いでいる。

\section{g4: \texttt{select} と \texttt{reply} の帰属}
\label{sec:g4}

\lstinputlisting{samples/guide/g4_select.aipl}

\end{term}

\texttt{case job(k)} の本体にある \texttt{reply} は \texttt{serve} ではなく
\texttt{job} への返信なので、\texttt{serve} は \ty{unit} のままでよい。

\texttt{select} で待つメッセージ名は、直接呼ばせない設計にするのが安全である。

\section{型と実行値の差分テスト}

型検査が付けた戻り値型と、実行時に実際に \texttt{reply} された値の型を
突き合わせるハーネスがある。

\begin{term}
python3 scripts/type_runtime_diff.py abclc/*.aipl docs/samples/guide/*.aipl
\end{term}

処理系側は \texttt{AIOS\_TYPE\_TRACE=1} のとき \texttt{reply} のたびに
\texttt{[rtype] Class\#method = tag} を出す。この仕組みで、整数演算が
\ty{float} を返していた不整合（$\vdash e : \ty{int}$ なのに
$e \Downarrow$ \texttt{VFloat}）が実際に見つかった。
わざと食い違う負例には
\texttt{// TYPE\_RUNTIME\_DIFF: expect-mismatch} と書いておけば既知として扱われる。

\textbf{型を変更したら必ず回すこと。} これが preservation の破れを見つける常設装置である。

\texttt{REMOTE\_REVIEWER\_HOSTPORT} & \texttt{remote\_review} の宛先 \\
\bottomrule
\end{tabular}
\end{center}

\section{実機で動かす --- Xinu / Raspberry Pi 3 と Pi 5}
\label{sec:xinu}

AIPL のプログラムは、\textbf{ベアメタルの Raspberry Pi 3}（Embedded Xinu）の上でも動く。
OS も libc も無く、カーネル自身がアクターの実行機構を持っている環境である。

\subsection{三つの実行系と、その役割分担}

\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
実行系 & 何をするか & 検査 \\
\midrule
OCaml 版 REPL（正典） & 型・効果・期限・七つの規律を検査する & \textbf{する} \\
ホスト VM（Mac） & \texttt{.avm} を実行し、値まで読める & しない \\
Xinu 実機（Pi 3） & カーネル内の VM が \texttt{.avm} を実行する & しない \\
Xinu 実機（Pi 5） & AIPL を C に直し、機内 \texttt{cc} が AArch64 に JIT する & しない \\
\bottomrule
\end{tabular}
\end{center}

ここが本節でいちばん大事な点である。\textbf{\texttt{.avm} 経路は型検査をしない。}
戻り値型の注釈 \texttt{: string}、義務レベル \texttt{@3}、効果 \texttt{!\{log\}} は
\textbf{構文としては受理するが、そのまま捨てる}。
静的な保証はすべて正典（OCaml 版）の側で得るものであり、
実機は\textbf{検査を通したものを走らせる場所}である。
つまり運用は二段構えになる ---
まず \S\ref{sec:tc} の型検査を通し、それから \texttt{.avm} に落として実機へ送る。

\subsection{\texttt{.avm} へのコンパイルと投入}

\texttt{.avm} は整数アクターのバイトコード（先頭 4 バイトが \texttt{AVM1}）で、
ホスト VM と Pi 3 とで\textbf{同じ形式}である。

\begin{term}
# 1. .aipl -> .avm
./_build/default/compile_avm.exe prog.aipl prog.avm

# 2. まずホスト VM で値を確かめる
./_build/default/server.exe 8099 --no-open
curl --data-binary @prog.avm "http://127.0.0.1:8099/actor/loadvm?ask=0"
curl "http://127.0.0.1:8099/api/console"

# 3. 実機へ送る（Pi 3 は 8080 番）
curl --data-binary @prog.avm "http://192.168.3.50:8080/actor/loadvm?ask=0"
loadvm: body=131 accepted=1 spawned actor id=1
\end{term}

\textbf{カーネルを焼き直す必要は無い。} \texttt{.avm} は動作中のカーネルに読み込まれ、
その場でアクターとして起動する。SD カードを差し替えるのは、
VM に\textbf{新しい命令}を足したときだけである。

\begin{itemize}
\item \textbf{\texttt{?ask=0} を落とすと応答が返らない。}
  付け忘れると 25 秒待っても 0 バイトのまま切れる。
  板の故障と間違えやすいので、まずここを疑うとよい。
\item 板は\textbf{立て続けの HTTP に弱い}。要求と要求の間は 2--4 秒空ける。
\end{itemize}

\subsection{実機で値を読む}

Pi 3 の \texttt{print} は\textbf{シリアルへ出る}ので、ネットワーク越しには読めない。
実機で戻り値を読む方法は、いまのところ\textbf{外部公開だけ}である
（\S\ref{sec:expose}）。

\lstinputlisting{samples/guide/g5_web.aipl}

\begin{term}
curl "http://192.168.3.50:8080/api/routes"
/echo -> a6

curl "http://192.168.3.50:8080/api/x/echo?method=say&args=hi"
echo: hi
\end{term}

\texttt{args} は URL エンコードを解いてから渡される（\texttt{\%20} と \texttt{+} が空白になる）。
返信を待つ上限は 90 秒で、返信が来た時点で抜ける。

\subsection{機内の小型モデル --- \texttt{ai\_call}}
\label{sec:xinu-ai}

Pi 3 のカーネルには\textbf{小型の言語モデルが焼き込んである}。
\texttt{ai\_call} は外部のサービスを呼ぶのではなく、\textbf{機内で推論する}。

\begin{center}
\small
\begin{tabular}{@{}ll@{}}
\toprule
モデル & \texttt{stories260K}（Llama 2 構成、\texttt{dim}=64・5 層・8 ヘッド・語彙 512） \\
規模 & 約 26 万パラメータ、fp32 で 1.06\,MB \\
置き場所 & カーネル像の \texttt{.rodata}（カーネルは 1.09\,MB $\to$ 2.16\,MB） \\
演算 & ソフト浮動小数点、D-cache 無効の 32 ビット A53 \\
実測 & \texttt{ai\_call} 1 回の往復が 2--6 秒（24 トークン生成） \\
\bottomrule
\end{tabular}
\end{center}

\begin{term}
curl "http://192.168.3.50:8080/api/x/sage?method=ask&args=Once%20upon%20a%20time"
MODEL[, there was a little girl named Lily. She loved to play outside in the p]END
\end{term}

効果表（\S\ref{sec:builtins}）で \texttt{ai\_call} は \eff{ai, net} とされているが、
Pi 3 では\textbf{機外に出ない}。効果検査は保守的に見積もる側なので、
実機で \eff{net} が実際には立たないことは検査の健全性を損なわない
（禁止しすぎることはあっても、見逃すことはない）。

\textbf{ホスト VM（Mac）はモデルを持っていない。}
そちらで \texttt{ai\_call} を呼ぶと
\texttt{(no local model on host)} を前置した文字列が返る。
それらしい応答を作って返すことはしない ---
モデルが無いことは、黙って隠すのではなく値に書いてある。

\subsection{実機側の限界}

\texttt{.avm} 経路が受け付けるのは、正典の言語の\textbf{部分集合}である。
足りないものは\textbf{その場でエラーになる}（黙って落ちることはない）。

\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
機能 & \texttt{.avm} 経路 & 備考 \\
\midrule
クラス・フィールド・\texttt{send} / \texttt{send!} & ○ & \\
メソッド局所の \texttt{var}・\texttt{reply} & ○ & 局所変数は隠しフィールドになる \\
\texttt{if} / \texttt{while} & ○ & \textbf{\texttt{while (c) do} と括弧が要る} \\
\texttt{now} / \texttt{future} / \texttt{await} / 期限 & ○ & \textbf{継続分割}で実現（下記） \\
\texttt{select} / \texttt{case} / \texttt{timeout} & ○ & \texttt{case} 名は実在のメソッドに限る \\
文字列（値・\texttt{++}・引数） & ○ & \\
\texttt{web\_listen} / \texttt{web\_expose} & ○ & \\
\texttt{ai\_call} & ○ & 機内モデル（\S\ref{sec:xinu-ai}） \\
\midrule
型・効果・レベルの注釈 & 受理して\textbf{捨てる} & 検査は正典側で \\
\ty{float}・浮動小数リテラル & × & 値は整数と文字列のみ \\
配列（\texttt{array\_*}） & × & \texttt{avm: unsupported expression} \\
数学組込み（\texttt{sqrt} 等） & × & 同上 \\
\texttt{spawn} & × & 同上 \\
\texttt{remote(...)} 送信 & × & \texttt{parse: unexpected token} \\
\texttt{replyto} & × & \texttt{avm: unknown variable} \\
\bottomrule
\end{tabular}
\end{center}

\textbf{継続分割}について一言。VM には「値を返す同期呼び出し」の命令が無い。
そこで \texttt{now} / \texttt{await} / \texttt{select} が現れる位置で
\textbf{メソッドを二つに割り}、続きを別メソッドとして生成している。
割った先へ値を渡すために、メソッド局所の \texttt{var} を
\textbf{アクターの隠しフィールド}にしてある。
\texttt{reply} の宛先も、分割後は \texttt{sender} が元の呼び出し元ではなくなるので、
メソッドに入った時点で呼び出し元を \texttt{\_\_snd} に退避している。
利用者から見た挙動は正典と同じだが、\textbf{生成されるメソッド数は元より多い}。

\subsection{Pi 3 は一度に一つのモジュールしか持てない}
\label{sec:pi3-onemodule}

Pi 3 の VM は\textbf{モジュール置き場を一つしか持たない}
（\texttt{static unsigned char vm\_mod[...]}）。
\texttt{/actor/loadvm} は\textbf{そこを上書きする}ので、
\textbf{生きているのは最後に読み込んだモジュールだけ}である。

これは黙って効く。先に登録した公開ルートは\textbf{そのまま残り}、
指し先のアクターだけが動かなくなる ---
呼んでも返信が来ず、\texttt{vm\_web\_call} の 90 秒を待ち切って空が返る。
実際、モジュールを 13 本続けて投入したあとでは、
最初に公開した \texttt{/sage} と \texttt{/echo} がどちらも無応答になり、
そのとき投入した新しいアクターだけが即座に応えた。

\begin{itemize}
\item \textbf{実機で試すときは 1 本ずつ}。投入したら、次を投入する前に確かめる。
\item ルート表（\texttt{/api/routes}）に古い項目が残っていても、
  それが生きている証拠にはならない。同じ名前が二重に並ぶこともある
  （検索は\textbf{先頭一致で打ち切る}ので、先に登録された方が選ばれる）。
\end{itemize}

\subsection{正典ガイド 10 本の実機確認}

第 \ref{part:sample} 部の g1--g10 は、いずれも \texttt{.avm} に落ちて
Pi 3 に読み込まれ、アクターとして起動する（10 本すべて \texttt{accepted=1}）。
ただし、この主張が言えるのは\textbf{1 本ずつ順に投入した場合}であって、
\textbf{10 本が同時に動くという意味ではない}
（\S\ref{sec:pi3-onemodule}）。
さらに \texttt{accepted=1} が言うのは「読み込んで走り出した」までで、
\textbf{出力の正しさまでは見ていない}。
値まで突き合わせられるのは外部公開した経路だけなので、
実機で出力まで確かめてあるのは g5（\texttt{/echo}）と、
\texttt{ai\_call} を公開した例（\texttt{/sage}）である。
それ以外の出力照合はホスト VM 側で行う。

\subsection{Pi 5 --- もう一つの実機}
\label{sec:xinu-pi5}

Pi 5（\texttt{192.168.3.101}）は\textbf{実行方式が違う}。
バイトコードを解釈するのではなく、AIPL を機内で C に直し、
機内の C コンパイラ \texttt{cc} が\textbf{その場で AArch64 の機械語に JIT} する。

\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
 & Pi 3 & Pi 5 \\
\midrule
実行方式 & \texttt{.avm} をカーネル内 VM が解釈 & AIPL$\to$C$\to$機内 \texttt{cc} が JIT \\
前段 & Mac 側の \texttt{compile\_avm} & \textbf{機内}の \texttt{abcl2c} \\
投入 & \texttt{POST /actor/loadvm?ask=0}（8080 番） & \texttt{POST /cc}（80 番） \\
値の読み方 & \texttt{web\_expose} + \texttt{/api/x/} & \texttt{/cc} の応答にそのまま出る \\
同時に持てるモジュール & \textbf{1 本だけ}（\S\ref{sec:pi3-onemodule}） & 実行のたびに JIT \\
値の種類 & 整数と文字列 & 整数・文字列・浮動小数・リスト \\
\texttt{ai\_call} & 命令 \texttt{0x52} & ランタイム \texttt{v\_ai\_call} \\
カーネル & 1.09\,MB $\to$ 2.16\,MB & 0.94\,MB $\to$ 2.02\,MB \\
\bottomrule
\end{tabular}
\end{center}

\subsubsection*{動かし方}

前段が\textbf{機内にある}ので、AIPL のソースをそのまま送れる。
本文の先頭が \texttt{class} なら \texttt{abcl2c} を通り、
そうでなければ C として扱われる。

\begin{term}
curl --data-binary @prog.abcl "http://192.168.3.101/cc"
MODEL[, there was a little girl named Lily. She loved to play outside in the p]END
=> 0
\end{term}

末尾の \texttt{=> 0} は \texttt{main} の戻り値である。
シェルからは \texttt{cc <file>} / \texttt{make <file>} が
\texttt{.abcl} / \texttt{.aipl} を透過的に扱う。
機内モデルは \texttt{llm <prompt>} でも直接叩ける（出力はシリアルへ）。

\subsubsection*{プログラムが何になるか}

利用者から見える形は AIPL のままだが、生成される C は読める。
クラスは\textbf{番号}になり、オブジェクトは配列 \texttt{g\_obj[]} の要素、
メソッドは \texttt{m\_<クラス>\_<メソッド>} という関数、
メソッド呼び出しは番号で引く \texttt{dispatch} になる。

\begin{term}
struct Obj { int cls; int f[1]; };   /* f[] がフィールド */
struct Obj g_obj[2048];
int m_Sage_ask(int self, int a0, int a1, int a2, int a3) { ... }
int dispatch(int self, int meth, int a0, int a1, int a2, int a3);
int main() { int v_s = v_int(g_spawn(0)); dispatch(v_int_of(v_s), 0, ...); }
\end{term}

\textbf{この \texttt{cc} では \texttt{int} が 8 バイトである}
（\texttt{cc/ccpriv.h} に明記）。AIPL のタグ付き 64 ビット値と幅が一致するので、
文字列（ヒープへのポインタ）を \texttt{int} の変数に入れても切り詰められない。

値はランタイム関数を通して扱う ---
\texttt{v\_int} \texttt{v\_str} \texttt{v\_floatlit} \texttt{v\_add} \texttt{v\_sub}
\texttt{v\_mul} \texttt{v\_div} \texttt{v\_lt} \texttt{v\_le} \texttt{v\_eq} \texttt{v\_ne}
\texttt{v\_and} \texttt{v\_or} \texttt{v\_not} \texttt{v\_truthy} \texttt{v\_int\_of}
\texttt{v\_print} \texttt{v\_ai\_call} \texttt{v\_list\_*}。
\texttt{v\_add} は片方が文字列なら\textbf{連結}になるので、
Pi 5 では \texttt{+} が数値加算と文字列連結を兼ねる（\texttt{++} は無い）。

\subsubsection*{機内の小型モデル}

\texttt{ai\_call} は \texttt{v\_ai\_call} に落ち、プロンプトを文字列に直して
\texttt{llm\_run} を呼び、結果を値ヒープに複写して文字列値で返す。
モデルは Pi 3 と\textbf{同じもの}（\S\ref{sec:xinu-ai}）で、
\texttt{ai\_call("Once upon a time")} は Pi 3・Pi 5・Mac の参照実装のいずれでも
72 バイト一致した。違うのは速さだけで、\textbf{Pi 5 は 1 回 0.42--0.64 秒}である。
Pi 3 は起動直後で 2--6 秒、モジュールを 13 本投入してアクターが積み上がった
状態では 16.6 秒だった（生成はトークンごとにスケジューラへ譲るので、
常駐アクターが増えるほど遅くなる。ただしこの因果関係は\textbf{まだ切り分けていない}）。

\subsubsection*{機内前段（\texttt{abcl2c}）が受け付ける範囲}

\begin{center}
\small
\begin{tabular}{@{}ll@{}}
\toprule
通る & クラス、フィールド、メソッド、\texttt{var}、代入、\texttt{if}/\texttt{else}、 \\
     & \texttt{while}（\texttt{do} は付けても付けなくてもよい）、\texttt{return}、 \\
     & \texttt{new}（\texttt{init} があれば引数を渡せる）、\texttt{now}（値を返す）、 \\
     & \texttt{send}、整数・文字列・浮動小数、\texttt{+ - * /}、比較、 \\
     & \texttt{print} / \texttt{puts}、\texttt{ai\_call} \\
\midrule
通らない & \textbf{型・レベル・効果の注釈}（\texttt{: string} で \texttt{method: expected '\{'}） \\
     & \texttt{reply} / \texttt{replyto} / \texttt{future} / \texttt{await} \\
     & \texttt{select} / \texttt{case} / \texttt{timeout} \\
     & \texttt{++}（\texttt{+} を使う）、配列 \texttt{array\_*}、\texttt{spawn}、\texttt{remote} \\
     & \texttt{print} / \texttt{puts} / \texttt{ai\_call} 以外の関数呼び出し \\
\bottomrule
\end{tabular}
\end{center}

断り方は名前つきで出る ---
\texttt{not supported on this device: future}、
\texttt{unknown function: sqrt}、
\texttt{new: class has no init to take arguments}。
\textbf{黙って別の意味にはならない}。

\textbf{この範囲は正典よりだいぶ狭い。}
\S\ref{part:sample} の g1--g10 は\textbf{どれもこの前段を通らない}
（すべて戻り値注釈を持つため）。
Pi 5 で動かすときは、注釈を落とし、\texttt{reply} の代わりに \texttt{return} と
\texttt{now} を使い、\texttt{++} を \texttt{+} に直す必要がある。
Pi 3 側の \texttt{.avm} 経路（\S\ref{sec:xinu}）は注釈を\textbf{受理して捨てる}ので、
そちらは正典のソースがそのまま通る --- 同じ「実機」でも前段の性格が違う。

\part{付録}
\label{part:appendix}

\section{文法の要約}

\begin{term}
program    ::= decl+

decl       ::= "class" ID "{" field* method+ "}"
             | "var" ID "=" expr ";"
             | "var" ID "=" "new" ID "(" args ")" ";"
             | "send"  target "." ID "(" args ")" ";"
             | "send!" target "." ID "(" args ")" ";"
             | ID "(" args ")" ";"

field      ::= "var"   ID "=" expr ";"
             | "float" ID "=" expr ";"

method     ::= "method" ID "(" params ")" ret? lvl? eff? "{" stmt+ "}"
params     ::= (param ("," param)*)?
param      ::= ID | ID ":" ClassName | ID ":" "reply"
ret        ::= ":" ("int"|"float"|"string"|"bool"|"unit"|"any"|ClassName)
lvl        ::= "@" INT                    -- 義務レベル。書かなければ推論
eff        ::= "!" "{" (ID ("," ID)*)? "}"

target     ::= ID
             | "remote" "(" STRING "," STRING ")"

stmt       ::= ID "=" expr ";"
             | "var" ID "=" expr ";"
             | "var" ID "=" "new" ID "(" args ")" ";"
             | ID "(" args ")" ";"
             | "call" ID "(" args ")" ";"
             | "send"  ("self"|"sender"|target) "." ID "(" args ")" ";"
             | "send!" target "." ID "(" args ")" ";"
             | "if" "(" expr ")" stmt ("else" stmt)?
             | "while" expr "do" stmt
             | "{" stmt* "}"
             | "select" "{" case* timeout_case? "}"

case         ::= "case" ID "(" ids? ")" "->" "{" stmt+ "}"
timeout_case ::= "timeout" INT "->" "{" stmt+ "}"

expr       ::= INT | FLOAT | STRING | "true" | "false" | ID
             | "-" expr
             | expr ("=="|"!="|">"|"<"|">="|"<="|"++"|"+"|"-"|"*"|"/") expr
             | "new" ID "(" args ")"
             | "now" target "." ID "(" args ")" deadline?
             | "future" target "." ID "(" args ")"
             | "await" expr deadline?
             | "replyto"                  -- 返信先を値として取り出す
             | ID "(" args ")"
             | "(" expr ")"

-- else を書くと tau、書かないと result<tau> になる
deadline   ::= "timeout" INT "else" expr
             | "timeout" INT
\end{term}

演算子の優先順位は弱い順に、
\texttt{==} \texttt{!=} $\;<\;$
\texttt{>} \texttt{<} \texttt{>=} \texttt{<=} $\;<\;$
\texttt{++} $\;<\;$
\texttt{+} \texttt{-} $\;<\;$
\texttt{*} \texttt{/} $\;<\;$ 単項マイナス。二項演算子は\textbf{すべて左結合}である（等値も含む）--- \texttt{1 == 2 == false} は \texttt{((1 == 2) == false)} と読まれて \texttt{true} になる。単項マイナスは前置なので重ねられる（\texttt{- - 3} は \texttt{3}）。

  型検査器と REPL の情報メッセージを抑止する \\
\texttt{AIOS\_STRICT\_PROTOCOL} &
  セッションの手順が静的に並べきれない場合の「やり残し」を警告する。
  既定は黙る（\S\ref{sec:session}） \\
\texttt{AIOS\_STRICT\_RESOURCE} &
  名前が文字列リテラルでない \texttt{acquire} の場所を知らせる。
  そこは順序を検査できない（\S\ref{sec:resorder}） \\
\texttt{AIOS\_SHOW\_LEVELS} &
  推論した義務レベルと、資源の全体順序を表示する \\
\texttt{AIOS\_LAX\_WAIT} &
  循環待ちの検出をエラーから警告に落とす。既定はエラー \\
\texttt{AIOS\_LAX\_ACTOR} &
  アクター型を区別しない（\texttt{actor(A)} と \texttt{actor(B)} を単一化する）。
  既定は区別する \\
\texttt{AIOS\_LAX\_ASSIGN} &
  未宣言の名前への代入を許す（従来動作）。既定はエラー \\
\texttt{AIOS\_MODEL\_PROVIDER} &
  \texttt{ai\_call} が使うモデル事業者。既定は \texttt{gemini} \\
\bottomrule
\end{tabular}
\end{center}

\noindent 例えば、期限を必ず書く規律で書きたければ

\begin{lstlisting}
AIOS_STRICT_DEADLINE=1 ./src/abclrepl_thread -q -f run.repl
\end{lstlisting}

\section{よくある落とし穴}

\begin{itemize}
\item \textbf{\texttt{now} は式である。} \texttt{now x.m();} は構文エラー。
  必ず \texttt{var r = now x.m() timeout 100 else 0;} のように受ける。
\item \textbf{\texttt{send} の宛先は変数}であってクラス名ではない。
\item \textbf{\texttt{now self.m()} は書けない}（自己デッドロックになるため
  文法で禁止されている）。計算を切り出したいなら別アクターへ。
\item \textbf{\texttt{var x = 0;} に後からアクターを代入できない}
  （\ty{int} に推論されている）。最初から \texttt{var x = new Foo();} で作る。
\item \textbf{文字列連結は \texttt{++}}。\texttt{+} は数値専用。
\item \textbf{フィールドはメソッドより前}に書く。
\item \textbf{待ちには期限を書く}。書かないと警告が出るし、
  \texttt{AIOS\_STRICT\_DEADLINE=1} では通らない。
\item \textbf{実機へ送るときは \texttt{?ask=0} を付ける}。
  \texttt{/actor/loadvm} に付け忘れると応答が返らず、板の故障に見える（\S\ref{sec:xinu}）。
\item \textbf{実機の \texttt{print} はシリアルに出る}。ネットワーク越しに値を読むには
  \texttt{web\_expose} して \texttt{/api/x/} を叩く。
\item \textbf{効果は申告すると検査される}（gradual）。申告しなければ
  何も言われない。書けば実体との差を突いてくる。
\end{itemize}

\section{現状の限界}

\begin{itemize}
\item \textbf{実機（Xinu / Pi 3）で動く範囲は正典の部分集合である。}
  \ty{float}・配列・数学組込み・\texttt{spawn}・\texttt{remote}・\texttt{replyto} が無く、
  型・効果・レベルの注釈は受理して捨てる（検査は正典側で行う）。詳細は \S\ref{sec:xinu}。
\item \texttt{future} + \texttt{await} に分けて書くと効果伝播を逃れる
  （\S\ref{sec:effects} の「既知の穴」）。修正には
  \ty{future} の型に効果を載せる必要がある。
\item 型注釈つきの変数宣言 \texttt{var x : T = e;} が無い。
\item \texttt{sender} は \ty{any} で、\texttt{send sender.m(...)} は
  メソッドの存在も型も検査されない。
\item リモート送信先（\texttt{remote(...)}）の戻り値は \ty{any} のまま。
  対向ノードのインタフェース記述を読み込む仕組みが無い。
\item メソッドの引数は単相で、多相なメソッドは書けない。
\item \ty{int} と \ty{float} の間に暗黙変換が無く、
  両辺が未束縛の \texttt{a + b} は注釈が必要。
\item 配列リテラル \texttt{[...]} は無い。
  \texttt{array\_empty} と \texttt{array\_push} で作る。
\item 返信先（\texttt{replyto}）を\textbf{フィールドに持てない}。
  引数として渡すことはできる（\S\ref{sec:reply1st}）。
  フィールドは初期化子から型が決まるので \texttt{var w = 0;} は \ty{int} になり、
  \texttt{w = replyto} が型不一致になる。
\item 資源の全体順序が追えるのは、名前が\textbf{文字列リテラル}の
  \texttt{acquire} だけである（\S\ref{sec:resorder}）。
\item セッションの静的検査が届くのは\textbf{同期の呼び先}までである
  （\S\ref{sec:session}）。
\item 停止性は保証されない。デッドロック自由は「詰まらない」であって
  「必ず終わる」ではない。\texttt{while 1 > 0 do \{\}} は止まらないが、
  それは待ちではない。
\end{itemize}
